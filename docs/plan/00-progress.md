- **The concurrency lock is a _write_ lock on a _working path_ — narrows blueprint §15D (resolved 2026-08-16, Phase 6):** §15D specifies `repoPath → boolean busy`, checked before starting **any** run. That is stricter than the hazard it exists for. What breaks is two agents mutating one working tree — half-applied edits, one agent reading a file another is rewriting, `.git/index.lock` contention — and a `read_only` persona does none of it. Under the literal rule a reviewer could not read a repo while a refactor was running, which is precisely the pair blueprint §16 Journey 2 is built around, so the rule would have defeated the demo it was written to protect.
  Resolved as: `read_only` takes a **shared** hold, anything that can write takes an **exclusive** one, readers are unlimited and never refused. Only writer-vs-writer serializes. Refusals name the holder and write no message row, since a persisted question nothing will answer reads as a lost message rather than a refusal. `src/main/services/run-lock.ts`, pure and unit-tested; Phase 7's @mentions and Phase 8's routines acquire through the same function.

Four documents said otherwise (this entry, `06-core-messaging.md:70`, the Phase 12 header, and Phase 7's own acceptance check), and three tests agreed with the code rather than the claim — one of them titled `lets a reader run while a writer holds the repo` while asserting the writer was refused, and another titled `lets a reader and a writer run together` while asserting neither could join the other. Fixed in Phase 7 Step 1: `shared` is now refused by nothing.
  **Corrected a second time, in the Phase 6/7 close-out — the other direction was wrong too.** The first fix left "an exclusive run is refused by _any_ holder", which still contradicted this entry's own "only writer-vs-writer serializes" and `07-group-coordination.md:42`: a writer was refused while a reader held. That is the same hazard read the other way round — the reader gets a mid-write snapshot, which is exactly what is already accepted when a reader starts under a writer — and refusing it meant one long `read_only` review could block every writer on the repo. `blockingHolder` now looks for an `exclusive` holder specifically. Shared holders are still recorded, because `listActiveRuns()` and the fleet indicator have to name everyone running; they simply refuse nobody. Two rounds of this on one function is the argument for writing the test from the claim rather than from the code.

Identical today — that function returns `contact.repoPath` — and it is the single place the worktree phase changes so two _writers_ can overlap as well. **(b)** How strong "readers cannot write" is depends on the backend, and the lock cannot tell you: `AgentCapabilities.sandboxEnforcement` reports `os` or `policy` per turn. Codex's `--sandbox read-only` has always been OS-enforced, and Claude's became so in the post-Phase-5 review; where the SDK has no sandbox implementation it degrades to our allowlist.
- **Worktree isolation adopted, deferred, and chosen per Contact (decided 2026-08-16, after Phase 6 planning):** the write lock above frees readers, but two _writing_ personas on one repo still queue. The answer is a `git worktree` per writing Contact — its own checkout, its own branch, one shared object store. Scoped as `12-worktree-isolation.md`, slotted between Phases 8 and 9 in execution order: Phase 7 needs nothing from it, Phase 8's scheduled writers are the first real contention, and Phase 9's Open PR is far better with a per-persona branch to push.

- **Hide-on-close, and the two things it quietly breaks (2026-08-16, Phase 8):** macOS already kept the process alive on window close, so the tray is not what _enables_ residency — it is what makes it visible and quittable. - **A worktree's git writes land outside the worktree (2026-08-16, Phase 12):** the phase doc said `SessionSpec.repoPath` becomes the worktree path "with **no change to `sandbox.ts`**". - **A message is stamped with the session that _answered_ it, at turn end (2026-08-17, Phase 22):** not at insert, and the dead-resume heal is what decides it. - **Isolation is mutable; `repoPath` is not; `branch` outlives `worktree_path` (2026-08-17, Phase 22):** isolation was documented as immutable in four places, and the argument was that a real checkout on disk points at those columns. `ensureWorktree` makes that false — the directory is created on the first _writing turn_, not at bind time — so the row is the durable thing and the disk follows it. The run guard here is load-bearing rather than defensive: the lock is keyed on `workingPathFor(contact)`, so moving it under a holder leaves that holder's release looking for a slot that no longer exists.
- **Recreate adopts the conversation; the cascade stays (2026-08-17, Phase 22):** the review's "leaving costs your history" was true — `messages` is ON DELETE CASCADE, so changing the one still-immutable binding traded a month of talk for a path. - **The composer's refusal is decided by the rule main uses (2026-08-17, Phase 22):** `ThreadView` predicted main's answer with a second reading and got it wrong three ways — comparing a run's working path against the contact's _repo_ path (so an isolated Contact was blocked by runs it can never collide with and unblocked by the one it can), ignoring the holder's lock mode, and ignoring its own. - **The theme preference moved to app_state, because main paints before the renderer exists (2026-08-19, theme ownership):** the window's `backgroundColor` is set at BrowserWindow construction and was derived from `nativeTheme.shouldUseDarkColors` — the *OS* theme — while the user's actual choice lived only in renderer `localStorage`, which main cannot read. Anyone running the app dark on a light system therefore watched it flash white on every launch, from the very line written to prevent flashing. `theme_preference` is now an app_state key, applied to `nativeTheme.themeSource` before the window is built, which makes the existing `shouldUseDarkColors` line correct without knowing the feature exists. Verified by mutation: drop the startup call and a stored dark preference paints `#FFFFFF` again. The renderer keeps its persisted copy deliberately, as a **first-paint cache** — `main.tsx` stamps the theme class synchronously before render, and an IPC round trip there would show the wrong theme for a frame — with `useThemeSync` reconciling it against app_state once the shell is up. Probed and rejected on the way: setting `themeSource` does *not* propagate to the renderer's `prefers-color-scheme`, so the renderer cannot simply follow the platform. Pane layout, `navExpanded` and `homeGuideOpen` stay in localStorage: no main-side consumer, and pane sizes churn on every drag.
- **`ask_writes` supersedes §15B for the personas that opt in (2026-08-18, Phase 24):** §15B's "the sandbox level, set once, is the approval — no per-action interrupts" stays the default posture and its reasoning stays sound; what changed is that both surrounding tools normalized per-action asks, and the all-or-nothing choice was forcing over-granting. The new level turns a would-be denial into a message-shaped decision in the thread rather than a modal, which is the §15B objection ("pausing a chat for a permission dialog") answered rather than overruled. The `read_only` command allowlist is reused as the ask/allow line — it is exactly the set already trusted to change nothing, and a false positive now costs one click instead of the whole command. Hard denials stay hard: writes outside the repo and `dangerouslyDisableSandbox` never become asks, because approval widens _when_ a write may happen, never _where_.
- **Approvals are Claude-only, stated rather than papered over (2026-08-18, Phase 24):** Claude's `canUseTool` is an async callback the SDK awaits, so the pause is a promise. Codex's `codex exec --experimental-json` stream has no approval-request event and no way to deliver an answer mid-turn — `approvalPolicy` reaches the CLI only as a `--config` value, and the SDK's event union confirms nothing could carry a reply. Same treatment as every other genuine divergence (§3): `askBeforeWritesSupported()` in shared/domain.ts is the single statement of the fact, the editors filter the option out on Codex and fall back to `read_only` on a backend switch, validation refuses the pairing at both doorways, and `codexSandboxMode('ask_writes')` maps to `read-only` so even an impossible row fails toward the posture's promise. Codex-via-app-server is possible in principle and recorded as out of scope, not forgotten.
- **An unanswered ask auto-denies at five minutes; nothing waits forever (2026-08-18, Phase 24):** Claude Code itself waits indefinitely on an approval, but there the human is at the terminal by definition; here the turn holds the repo's write lock while the user may be asleep — the exact wedge the §B5 watchdog closed. Five minutes is deliberately under the watchdog's ten, so a held ask can never read as backend silence, and the deny reason tells the model it was the clock, not the user. The registry settles every ask exactly once (human, timeout, or turn teardown), pending asks ride on `runs.list` + `runs-changed` rather than a new channel, and the card is live-only — the durable record is the tool-call row an approved write produces, the same treatment error bubbles get. Remembered allowlists ("always allow `npm test`") are the natural follow-on and deliberately not started: a durable grant needs review/revoke UI, which is its own phase.
- **The diff viewer's Split toggle had never split on a normal window (2026-08-19, UI pass):** reported as "two sets of line numbers", which is exactly what Monaco's _inline_ view draws — original gutter then modified gutter. `renderSideBySide` was being passed and ignored: `useInlineViewWhenSpaceIsLimited` defaults to `true` against a `renderSideBySideInlineBreakpoint` of 900, and the branch pane hands the editor its own width less the 224px file rail, so anything under about a 1900px window silently rendered inline while the control read "Split". The general rule worth keeping is not about this option: **a vendor widget that silently substitutes a different rendering will make our control lie, and the only way to find it is to look at the thing on a normal-sized window.** Two more defects wearing the same symptom, both real and both found while chasing it. Monaco's `ignoreTrimWhitespace` also defaults to `true`, so an edit to leading or trailing whitespace rendered as _nothing_ while git reported an insertion and a deletion — a review pane hiding a change git found. And `git diff --name-status` reports `M` for a **mode-only** change (644→755) whose two blobs are byte-identical, plus `R100` for a rename that edited nothing, so both arrive as ordinary pairs and render as a whole unmarked file. `noVisibleChangeNote` says which it is _above_ the editor rather than instead of it, and normalises line endings first, because Monaco's models hold one EOL per document — a CRLF→LF commit is two different strings that render as two identical files. The mode-only claim is asserted against real git in `git-diff.test.ts`; it is a claim about git's output, so a fabricated fixture would only have tested our reading of the manual.
- **Base UI writes string state as `data-<key>="<value>"`, and `Separator` had no size because of it (2026-08-19, UI pass):** `ui/separator.tsx` styled itself with `data-horizontal:` / `data-vertical:` variants, but `getStateAttributesProps` only collapses a state to a bare `data-<key>` when the value is boolean `true`; a string value becomes `data-<key>="<value>"`. Separator's state is `{ orientation: 'horizontal' }`, so the element carries `data-orientation="horizontal"` and neither variant ever matched — a `bg-border` div of zero pixels in both orientations. Invisible for as long as it has existed because its only consumer was `SidebarSeparator`, which nothing renders. Worth recording as a rule rather than a fix, since this codebase is Base UI throughout: **a `data-x:` variant is only correct for a boolean state; anything with a value needs `data-[x=value]:`.**
- **Home was one column, and the sparkline drew only the days that had spend (2026-08-19, UI pass):** four sections at 2/2/3/3 column counts, so a single waiting branch drew at half width and a single scheduled run at a third, and the summary ran past the fold before the guide started. Now a stat header, then the conversation and the work-waiting-on-a-human side by side, with the guide folded by default — the fresh-install and nothing-to-report paths already return the whole `WorkspaceGuide` pane, so starting closed loses nothing. Recent packs against `@container/main`, its own column, rather than `@container/pane`: the rail takes a third of the pane, so a pane-width query goes two-across at a width the column does not have — the same class of mistake as the `sm:` variants `PaneBody` replaced, one level further in. The instructive half is the chart. It was recharts at 40px tall, and recharts draws no rectangle for a zero-height bar, so `dailySpend`'s deliberate zero-fill — added precisely so a quiet week would not compress — rendered as _gaps_, and a week with three busy days became three blocks floating in an empty box with nothing to read them against. Seven divs always draw seven days; the track behind each one is what makes a quiet day legible as a quiet day, and `spendBarPercents` gives a day that spent something a floor so a real turn is never drawn as nothing. **A shape made of seven rectangles does not need a charting library, and at sparkline sizes the library is actively working against you.**
