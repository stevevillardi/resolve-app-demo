## Decisions made during planning (not in blueprint, resolve ambiguity)

- **Package manager:** npm.
- **Electron tooling:** electron-vite (main/preload/renderer, HMR) + electron-builder for packaging.
- **Repo structure:** single package, not a monorepo — schema stays small enough per blueprint §11 that pnpm workspaces would be overhead.
- **Phase 3 scope:** Claude/Codex SDK auth (blueprint §15A) and GitHub OAuth Device Flow (blueprint §9) are done together as one "app auth" phase, since both gate any real persona/contact work and share first-run onboarding UI.
- **Plan docs location:** `/docs/plan/`, numbered filenames, this tracker as `00-progress.md`.
- **Main↔renderer bridge — supersedes blueprint §11/§2 (resolved 2026-08-15, during Phase 1 planning):** `electron-trpc` is a no-go. Verified via live npm registry + GitHub API checks against the version we'd actually be running: latest release `0.7.1` published 2024-12-07 (~20 months stale); open, unresolved issue #227 "Compatibility with @trpc/client v11" (opened 2025-06-13); open issue #229 "Error when used with `moduleResolution: Bundler`" (opened 2025-11-18) — the electron-vite scaffold uses bundler resolution by default, so this isn't a theoretical edge case. The one v11-targeting fork (`trpc-electron`) is equally stale (single release, ~19 months old, no follow-up). Blueprint §11 itself flagged "verify actively maintained... early" as a gate for this exact package — this is that verification, and it failed.
  Replaced with a hand-rolled, Zod-validated typed IPC layer (`src/shared/ipc-contract.ts` as the single source of truth for procedure name → input/output schema, `ipcMain.handle`/`ipcRenderer.invoke` underneath). Built in Phase 1 (see `01-bootstrap.md`). Preserves the original goal (single typed contract, validated at the boundary, no per-procedure bespoke preload methods) without the dependency risk. Where any phase doc says "tRPC procedure" or "tRPC subscription," read it as "IPC procedure" / the IPC layer's streaming primitive — phase docs 03-06 have been updated accordingly. If `electron-trpc` ships a real v11-compatible release later, migration is contained to `src/main/ipc/*` and `src/renderer/src/lib/ipc-client.ts` — not a blocker for any phase.
- **Tailwind version — clarifies blueprint §11 (resolved 2026-08-15):** Tailwind is v4 (CSS-first config: `@import "tailwindcss"` + `@tailwindcss/vite` plugin), not the v3 `tailwind.config.js`/`postcss.config.js` pattern implied by older tutorials. Built in Phase 1.
- **Supporting screens are workspace views, not overlays — supersedes blueprint §11 (resolved 2026-08-15, during the design-system overhaul):** blueprint §11 justifies shadcn by noting that `Dialog`/`Sheet`/`Popover` "cover persona editor, new-contact flow, skill library, routine editor," which the first Phase 2 pass took literally — all five secondary screens opened as modals from a six-icon strip in the sidebar footer. That put the persona editor, the skill library, and the whole usage dashboard into `sm:max-w-md`/`sm:max-w-lg` boxes, and gave the app no navigation model beyond "pick a conversation."
  Resolved in favour of a three-pane shell: an icon nav rail (shadcn `Sidebar`, `collapsible="icon"`, ⌘B) → a resizable list panel → a content pane, with Chats, Personas, Skills, Routines, and Usage each a master-detail section. `NewContactFlow` and `GitHubConnectDialog` stay modal, since both are short decision-shaped flows you finish and dismiss rather than places you work. The component names from §10 are unchanged — `PersonaDetailPanel`, `SkillLibraryView`, `RoutineEditor`, and `UsageDashboard` are the same files, rendering inline instead of inside a `Sheet`/`Dialog` — so §10 coverage still holds. Blueprint §11's reasoning about _which_ shadcn primitives are needed is unaffected; only the placement of four screens changed. See `docs/plan/02-design-system.md`'s "Revision" section for the full scope of that pass.
- **`GitHubConnectDialog` scope — supersedes `02-design-system.md`'s exclusion list (resolved 2026-08-15, during Phase 2):** `02-design-system.md` explicitly excludes `GitHubConnectDialog` from Phase 2 ("that's Phase 3, since it's tied to actual auth state"), but `03-app-auth.md` assumes a Phase-2-built shell already exists to wire real device-flow state into. Resolved in favor of building a minimal, fully static `GitHubConnectDialog` shell in Phase 2 alongside the other 15 components — 4 prop-driven states (`not_connected` / `awaiting_authorization` / `polling` / `connected`), no OAuth logic, no IPC calls — so Phase 3 has a shell to wire into instead of building UI and auth logic simultaneously, consistent with how every other screen in this phase is handled. Not counted against Phase 2's own acceptance checks (decorative/out-of-scope for behavior, in-scope for visual shell only). See `src/renderer/src/components/github/GitHubConnectDialog.tsx`.
- **Codex SDK has no login API — supersedes blueprint §15A (resolved 2026-08-16, during Phase 3):** §15A states that Codex's SDK reuses existing auth automatically "with its own device-code browser login if none exists," and `03-app-auth.md` called this "load-bearing for this whole phase's UX." Verified against the published `@openai/codex-sdk@0.147.0`: the package exports only `Codex`, `Thread`, `startThread`/`resumeThread`, and `CodexOptions { codexPathOverride, baseUrl, apiKey, config, env }`. There is no login, auth, or device-code API. The assumed behaviour belongs to the `codex` CLI, which the SDK vendors (`dependencies: { "@openai/codex": "0.147.0" }`, platform binaries under `@openai/codex-<triple>/vendor/`).
  Resolved by driving the vendored binary directly from `src/main/services/codex-auth.ts`: `codex login status` for detection (exit 0/1 — more truthful than sniffing `~/.codex/auth.json`, since it catches expired credentials), `codex login --device-auth` for sign-in, and `codex login --with-api-key` (stdin, never argv) as the fallback. This landed better than the blueprint's assumption: `--device-auth` produces a URL + one-time code with the same shape as GitHub's device flow, so both providers share one `DeviceFlowState` in the contract and one `DeviceCodeDisplay` component. Both SDKs' vendored binaries are `asarUnpack`ed in `electron-builder.yml` and confirmed executable from inside a packaged `.app`.
- **Claude auth detection via `Query.accountInfo()` (resolved 2026-08-16, Phase 3):** `@anthropic-ai/claude-agent-sdk@0.3.233` bundles the Claude Code CLI through platform `optionalDependencies`, so nothing needs installing. `accountInfo()` returns `{ email, organization, subscriptionType, tokenSource, apiKeySource, apiProvider }` and resolves **without consuming a turn**, as long as the query gets a prompt stream that never yields and is `close()`d after. No fallback to probing `~/.claude/.credentials.json` was needed. Note `options.env` _replaces_ the subprocess environment rather than merging — `process.env` must be spread explicitly.
- **Domain model is shared, not renderer-local (resolved 2026-08-16, Phase 4):** the eight blueprint §4 entity types lived in `src/renderer/src/types/*.ts`, which would have forced main to redeclare all of them to write the same rows. Moved to `src/shared/domain.ts` as Zod schemas with `z.infer` types — the pattern `ipc-contract.ts` already used — so the Drizzle tables, the IPC contract, and the renderer are one definition rather than three kept in agreement by hand. `src/renderer/src/types/index.ts` re-exports them, so `@/types` still resolves and not one of the thirteen consuming components changed an import. The only renderer-local survivors are `MessageBubbleStatus`/`MessageBubbleError`, which are transient UI state (see the next entry) and `UsageSummary`, which is computed for display and never stored.
- **`messages` gets no `status`/`error` column — clarifies blueprint §12 (resolved 2026-08-16, Phase 4):** §12 lists `messages` as exactly `id, contact_id, role, content, timestamp`, while Phase 2's renderer `Message` type also carries `status` (`sent`/`streaming`/`error`) and a structured `error`. Those two describe a turn that is currently in flight, not a stored fact — a message reloaded from disk is by definition finished — so no columns were added. The persisted shape is `messageSchema` in `src/shared/domain.ts`; `src/renderer/src/types/message.ts` extends it with the transient pair. Recorded because the tempting fix in Phase 6 is to persist them.
- **Seeding is guarded by a marker, not by emptiness (resolved 2026-08-16, Phase 4):** first run inserts 5 skills and 3 persona templates from `src/main/db/seed-data.ts` and writes `app_state.seed_version`. The obvious alternative — seed when the tables are empty — silently resurrects content the user deliberately deleted on the next launch, so the marker records that seeding _happened_ rather than what survived it. Contacts and Groups are deliberately not seeded: they bind to a real local repo path, which nothing can know until Phase 6. The seed reuses the same ids as `src/renderer/src/mocks/` so the screens still on mock data (`RoutineList`, `UsageDashboard`, `UsageScopeList`) keep joining against the now-real personas instead of rendering orphans.
- **Delete semantics: block a persona, detach a skill (resolved 2026-08-16, Phase 4):** blueprint §12 defines no cascade rules. Deleting a PersonaTemplate with bound Contacts is refused with an error naming them (`contacts.persona_template_id` is `ON DELETE RESTRICT`; the service check exists so the failure is legible rather than "FOREIGN KEY constraint failed"). Deleting a Skill succeeds and strips its id from every persona's `skill_ids` in one transaction — `skill_ids` is a JSON array with no FK behind it, and a skill is injected text, so losing one degrades a persona's instructions rather than breaking the persona. Blocking there would have forced hand-unattaching it everywhere first.
- **`PRAGMA foreign_keys = ON` is mandatory and easy to miss (2026-08-16, Phase 4):** better-sqlite3 leaves foreign keys **off** by default, which would make every `references()` in `src/main/db/schema.ts` decorative — including the RESTRICT the persona-delete rule above depends on. Set in `src/main/db/create.ts`, with a test that bypasses the service check and asserts SQLite itself blocks the delete, so it can't silently regress. Related: `cost_usd` is a REAL column, not the INTEGER that Drizzle's `integer()` would have made it — a turn costs fractions of a cent.
- **Two migrations, not one, to drop `_bootstrap_check` (2026-08-16, Phase 4):** drizzle-kit prompts about rename-vs-drop when a table disappears, and that prompt needs a TTY, so adding eight tables while deleting one fails outright in a non-interactive shell. Split into `0002_add_blueprint_schema` (additive only) and `0003_drop_bootstrap_check` (deletion only), which are each unambiguous and read better as history anyway.
- **`app_state` table is permanent (Phase 3; honoured by Phase 4):** Phase 3 adds a `app_state` key/value table (`drizzle/0001_pretty_warlock.sql`) holding `onboarding_completed`, `github_account_login`, `github_scopes`. Unlike `_bootstrap_check`, Phase 4 **inherited** this table rather than dropping it, and added `seed_version` to it. Non-secret metadata only — the encryption boundary is `src/main/services/secrets.ts`, the sole permitted `safeStorage` caller (enforced by a `no-restricted-properties` rule in `eslint.config.mjs`), which writes keychain-encrypted files to `userData/secrets/*.bin` rather than to SQLite so that "no credential is in the database" holds by construction.
- **Env var prefix — clarifies Phase 1 config (resolved 2026-08-16, Phase 3):** electron-vite exposes only `MAIN_VITE_`-prefixed `.env` vars to the main process; an unprefixed name is invisible to `import.meta.env`. Rather than force a rename of the existing `GITHUB_CLIENT_ID`, `electron.vite.config.ts` widens `envPrefix` for main to `['MAIN_VITE_', 'GITHUB_']`, and `github-auth.ts` reads either spelling. See `.env.example`. A device-flow client ID has no accompanying client secret, so build-time inlining is not a leak.
- **Launch splash added to Phase 3 scope (2026-08-16, at the user's request):** so the first-run path is complete end to end — splash → onboarding → shell, with no unstyled seam. Implemented in-renderer (`components/launch/SplashScreen.tsx`) rather than as a second `BrowserWindow`, because `src/main/index.ts` already suppresses the pre-paint gap via `show: false` + `backgroundColor` + `ready-to-show`; the only gap a user actually perceives is the `auth.getStatus` round trip, which only the renderer can observe. Held for a 650ms minimum so a warm start doesn't flash it, and cross-faded so the seam reads as intentional. `App.tsx` is now the launch-flow router.
- **Tests are part of finishing a phase (established 2026-08-16, retroactively for Phases 1–3):** Phases 1–3 all shipped with no tests and no harness — manual verification proved each phase once but left nothing behind to catch a regression in a later one. From here, a phase is not `Done` until whatever in it warrants tests has them, and the testing scope is called out as part of the phase rather than bolted on afterwards.
  Harness: **Vitest** (`vitest.config.ts`, two projects — `main` in node with `electron` mocked, `renderer` in jsdom) and **Playwright** for Electron E2E (`playwright.config.ts`, `e2e/`). `npm test` runs the unit suite and is now a gate inside `npm run build`, so packaging can't ship a red suite; `npm run test:e2e` builds first, then drives the real app. Judgement on what to cover: pure logic, state machines, and process-boundary contracts yes; purely presentational components that only render mock data, no.
  What the retroactive pass covers: the IPC dispatch/validation layer (Phase 1), the `format`/`usage`/`theme` helpers (Phase 2), and all six Phase 3 auth services. 183 unit tests plus 14 E2E; ~83% statement coverage over `src/main`, `src/shared`, and `src/renderer/src/lib`.
  Two things worth knowing before writing more: **(a)** E2E redirects `HOME` and `CODEX_HOME` at a throwaway profile so a run can never touch real credentials, but Claude Code's login lives in the **macOS Keychain**, so it is _not_ isolable that way — E2E asserts the shape of `claude` rather than that it is signed out. **(b)** The nav rail's labels are `display:none` while collapsed, so its buttons have no accessible name; use `[data-slot="sidebar"]` (see `waitForShell` in `e2e/fixtures.ts`) rather than role/name queries.
  Two more added in Phase 4: **(c)** database-backed services are tested against a real `:memory:` SQLite with the actual checked-in migrations applied (`createTestDb` in `src/main/db/test-db.ts`) rather than hand-written `CREATE TABLE`s — a copy of the DDL drifts from the migration the moment either changes, and the drift looks like a passing test. This is also why `createDb` sits in `src/main/db/create.ts` apart from the electron-importing `index.ts`. **(d)** In E2E, use `waitForBridge` rather than `waitForShell` when a test only needs IPC: the shell doesn't exist until onboarding is complete, so waiting on the sidebar in a profile that hasn't onboarded times out against the splash.
  One more added in Phase 5: **(e)** anything that talks to a vendor SDK is split into a pure normalization layer plus a thin call, and the pure layer is tested against event shapes _captured from real runs_ with the SDK mocked. Fabricated fixtures test our reading of the docs rather than the SDK, which is exactly the failure mode Phase 5 found five times over. Two cases are worth copying: an unmodelled message type must be ignored rather than throw (Claude's `SDKMessage` union has 35+ variants and grows every release), and a thrown failure must still produce `error` then `done`. Live behaviour that costs money to observe belongs in the phase doc's "Verified live" section, not in a test — and `npm run probe:adapters` exists so it can be re-observed on demand.
- **Claude token accounting: read `modelUsage`, never sum assistant messages — supersedes blueprint §3 (resolved 2026-08-16, Phase 5):** §3 says to "dedupe per-step assistant messages sharing an id before summing." A captured multi-tool turn shows both halves are wrong for `@anthropic-ai/claude-agent-sdk@0.3.233`. Duplicate ids are real (15 assistant messages, 7 distinct ids), but deduping and summing those 7 gives **13 output tokens** against an actual **1045** — the per-message `usage` is a running snapshot, not a per-step total. The SDK's own annotations say `usage` is main-loop-only and that `modelUsage` is "the correct field for token/cost accounting." The real trap is different: `total_cost_usd` and `modelUsage` are cumulative across turns _within a streaming-input session_, avoided structurally by issuing one `query()` per turn with `resume` so each result covers exactly one turn.
- **Adapters import neither `electron` nor the database (2026-08-16, Phase 5):** same rule that put `createDb` in its own file. `src/main/adapters/` takes resolved skills from its caller and takes the Codex binary path through `AdapterConfig` rather than calling `resolveCodexBinary()` itself. This is what lets `npm run probe:adapters` drive a real backend outside Electron, and why the normalization has tests that cost nothing to run. `AgentAdapter.createSession` therefore takes a spec object rather than blueprint §3's literal `(persona, repoPath)`.
- **`@openai/codex-sdk` is ESM-only; main is CommonJS (2026-08-16, Phase 5):** its exports map declares an `import` condition and no `require`, so `require()` fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`. Phase 3 never hit this because `codex-auth.ts` imports only types, which erase at compile time. Resolved with `await import()` in `src/main/adapters/codex.ts`, which electron-vite preserves verbatim in the CJS bundle. Not a bundler config change — worth knowing before anyone "tidies" it into a static import.
- **Sandbox enforcement is a deny layer, not a complete mediator (2026-08-16, Phase 5):** Claude's SDK classifier decides first and only calls `canUseTool` for tool uses it would otherwise prompt about, so `echo hello` and `pwd && ls` ran without reaching our gate. `src/main/adapters/sandbox.ts` therefore narrows the prompt-worthy set rather than defining the whole policy; `disallowedTools` strips the write tools outright at `read_only` as the other layer. Verified where it matters: `touch` and `rm` are denied and the target file stays absent. Codex is the opposite shape — its `--sandbox read-only` preset is OS-enforced, and a write attempt fails with `operation not permitted`.
- **Codex model choice is auth-dependent, and must be explicit (2026-08-16, Phase 5):** codex-cli 0.147.0 knows `gpt-5.2-codex` and `gpt-5.3-codex`, but a ChatGPT account rejects both with a 400. `gpt-5.5` works. Because the event stream never names the model and `~/.codex/config.toml` can pick a different one per machine, the adapter always passes one explicitly — otherwise a `UsageEvent` would be priced against a guess. An unpriced model reports `costUsd: null`, never `0`, so "we don't know" can't be misread as "free".
- **`codex login status` does not detect expired credentials (2026-08-16, Phase 5):** it reported "Logged in using ChatGPT" and exit 0 against a refresh token that had already been consumed, while every turn failed with a 401. Phase 3 chose that command over sniffing `~/.codex/auth.json` specifically because it was believed to catch expired credentials — it does not. Not fixed here (Phase 5 touches no auth code), but `src/main/services/codex-auth.ts` should not be trusted as a liveness check.
