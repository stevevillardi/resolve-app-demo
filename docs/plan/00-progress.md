## Decisions made during planning (not in blueprint, resolve ambiguity)

- **Package manager:** npm.
- **Electron tooling:** electron-vite (main/preload/renderer, HMR) + electron-builder for packaging.
- **Repo structure:** single package, not a monorepo — schema stays small enough per blueprint §11 that pnpm workspaces would be overhead.
- **Phase 3 scope:** Claude/Codex SDK auth (blueprint §15A) and GitHub OAuth Device Flow (blueprint §9) are done together as one "app auth" phase, since both gate any real persona/contact work and share first-run onboarding UI.
- **Plan docs location:** `/docs/plan/`, numbered filenames, this tracker as `00-progress.md`.
- **Main↔renderer bridge — supersedes blueprint §11/§2 (resolved 2026-08-15, during Phase 1 planning):** `electron-trpc` is a no-go. Verified via live npm registry + GitHub API checks against the version we'd actually be running: latest release `0.7.1` published 2024-12-07 (~20 months stale); open, unresolved issue #227 "Compatibility with @trpc/client v11" (opened 2025-06-13); open issue #229 "Error when used with `moduleResolution: Bundler`" (opened 2025-11-18) — the electron-vite scaffold uses bundler resolution by default, so this isn't a theoretical edge case. The one v11-targeting fork (`trpc-electron`) is equally stale (single release, ~19 months old, no follow-up). Blueprint §11 itself flagged "verify actively maintained... early" as a gate for this exact package — this is that verification, and it failed.
  Replaced with a hand-rolled, Zod-validated typed IPC layer (`src/shared/ipc-contract.ts` as the single source of truth for procedure name → input/output schema, `ipcMain.handle`/`ipcRenderer.invoke` underneath). Built in Phase 1 (see `01-bootstrap.md`). Preserves the original goal (single typed contract, validated at the boundary, no per-procedure bespoke preload methods) without the dependency risk. Where any phase doc says "tRPC procedure" or "tRPC subscription," read it as "IPC procedure" / the IPC layer's streaming primitive — phase docs 03-06 have been updated accordingly. If `electron-trpc` ships a real v11-compatible release later, migration is contained to `src/main/ipc/*` and `src/renderer/src/lib/ipc-client.ts` — not a blocker for any phase.
- **Tailwind version — clarifies blueprint §11 (resolved 2026-08-15):** Tailwind is v4 (CSS-first config: `@import "tailwindcss"` + `@tailwindcss/vite` plugin), not the v3 `tailwind.config.js`/`postcss.config.js` pattern implied by older tutorials. Built in Phase 1.
- **Supporting screens are workspace views, not overlays — supersedes blueprint §11 (resolved 2026-08-15, during the design-system overhaul):** blueprint §11 justifies shadcn by noting that `Dialog`/`Sheet`/`Popover` "cover persona editor, new-contact flow, skill library, routine editor," which the first Phase 2 pass took literally — all five secondary screens opened as modals from a six-icon strip in the sidebar footer. That put the persona editor, the skill library, and the whole usage dashboard into `sm:max-w-md`/`sm:max-w-lg` boxes, and gave the app no navigation model beyond "pick a conversation."
  Resolved in favour of a three-pane shell: an icon nav rail (shadcn `Sidebar`, `collapsible="icon"`, ⌘B) → a resizable list panel → a content pane, with Chats, Personas, Skills, Routines, and Usage each a master-detail section. `NewContactFlow` and `GitHubConnectDialog` stay modal, since both are short decision-shaped flows you finish and dismiss rather than places you work. The component names from §10 are unchanged — `PersonaDetailPanel`, `SkillLibraryView`, `RoutineEditor`, and `UsageDashboard` are the same files, rendering inline instead of inside a `Sheet`/`Dialog` — so §10 coverage still holds. Blueprint §11's reasoning about _which_ shadcn primitives are needed is unaffected; only the placement of four screens changed. See `docs/plan/02-design-system.md`'s "Revision" section for the full scope of that pass.
- **`GitHubConnectDialog` scope — supersedes `02-design-system.md`'s exclusion list (resolved 2026-08-15, during Phase 2):** `02-design-system.md` explicitly excludes `GitHubConnectDialog` from Phase 2 ("that's Phase 3, since it's tied to actual auth state"), but `03-app-auth.md` assumes a Phase-2-built shell already exists to wire real device-flow state into. Resolved in favor of building a minimal, fully static `GitHubConnectDialog` shell in Phase 2 alongside the other 15 components — 4 prop-driven states (`not_connected` / `awaiting_authorization` / `polling` / `connected`), no OAuth logic, no IPC calls — so Phase 3 has a shell to wire into instead of building UI and auth logic simultaneously, consistent with how every other screen in this phase is handled. Not counted against Phase 2's own acceptance checks (decorative/out-of-scope for behavior, in-scope for visual shell only). See `src/renderer/src/components/github/GitHubConnectDialog.tsx`.
- **Codex SDK has no login API — supersedes blueprint §15A (resolved 2026-08-16, during Phase 3):** §15A states that Codex's SDK reuses existing auth automatically "with its own device-code browser login if none exists," and `03-app-auth.md` called this "load-bearing for this whole phase's UX." Verified against the published `@openai/codex-sdk@0.147.0`: the package exports only `Codex`, `Thread`, `startThread`/`resumeThread`, and `CodexOptions { codexPathOverride, baseUrl, apiKey, config, env }`. There is no login, auth, or device-code API. The assumed behaviour belongs to the `codex` CLI, which the SDK vendors (`dependencies: { "@openai/codex": "0.147.0" }`, platform binaries under `@openai/codex-<triple>/vendor/`).
  Resolved by driving the vendored binary directly from `src/main/services/codex-auth.ts`: `codex login status` for detection (exit 0/1 — more truthful than sniffing `~/.codex/auth.json`, since it catches expired credentials), `codex login --device-auth` for sign-in, and `codex login --with-api-key` (stdin, never argv) as the fallback. This landed better than the blueprint's assumption: `--device-auth` produces a URL + one-time code with the same shape as GitHub's device flow, so both providers share one `DeviceFlowState` in the contract and one `DeviceCodeDisplay` component. Both SDKs' vendored binaries are `asarUnpack`ed in `electron-builder.yml` and confirmed executable from inside a packaged `.app`.
- **Claude auth detection via `Query.accountInfo()` (resolved 2026-08-16, Phase 3):** `@anthropic-ai/claude-agent-sdk@0.3.233` bundles the Claude Code CLI through platform `optionalDependencies`, so nothing needs installing. `accountInfo()` returns `{ email, organization, subscriptionType, tokenSource, apiKeySource, apiProvider }` and resolves **without consuming a turn**, as long as the query gets a prompt stream that never yields and is `close()`d after. No fallback to probing `~/.claude/.credentials.json` was needed. Note `options.env` _replaces_ the subprocess environment rather than merging — `process.env` must be spread explicitly.
- **Domain model is shared, not renderer-local (resolved 2026-08-16, Phase 4):** the eight blueprint §4 entity types lived in `src/renderer/src/types/*.ts`, which would have forced main to redeclare all of them to write the same rows. Moved to `src/shared/domain.ts` as Zod schemas with `z.infer` types — the pattern `ipc-contract.ts` already used — so the Drizzle tables, the IPC contract, and the renderer are one definition rather than three kept in agreement by hand. `src/renderer/src/types/index.ts` re-exports them, so `@/types` still resolves and not one of the thirteen consuming components changed an import. The only renderer-local survivors are `MessageBubbleStatus`/`MessageBubbleError`, which are transient UI state (see the next entry) and `UsageSummary`, which is computed for display and never stored.
- **`messages` gets no `status`/`error` column — clarifies blueprint §12 (resolved 2026-08-16, Phase 4):** §12 lists `messages` as exactly `id, contact_id, role, content, timestamp`, while Phase 2's renderer `Message` type also carries `status` (`sent`/`streaming`/`error`) and a structured `error`. Those two describe a turn that is currently in flight, not a stored fact — a message reloaded from disk is by definition finished — so no columns were added. The persisted shape is `messageSchema` in `src/shared/domain.ts`; `src/renderer/src/types/message.ts` extends it with the transient pair. Recorded because the tempting fix in Phase 6 is to persist them.
- **Seeding is guarded by a marker, not by emptiness (resolved 2026-08-16, Phase 4):** first run inserts 5 skills and 3 persona templates from `src/main/db/seed-data.ts` and writes `app_state.seed_version`. The obvious alternative — seed when the tables are empty — silently resurrects content the user deliberately deleted on the next launch, so the marker records that seeding _happened_ rather than what survived it. Contacts and Groups are deliberately not seeded: they bind to a real local repo path, which nothing can know until Phase 6. The seed reuses the same ids as `src/renderer/src/mocks/` so the screens still on mock data (`RoutineList`, `UsageDashboard`, `UsageScopeList`) keep joining against the now-real personas instead of rendering orphans.
- **Delete semantics: block a persona, detach a skill (resolved 2026-08-16, Phase 4):** blueprint §12 defines no cascade rules. Deleting a PersonaTemplate with bound Contacts is refused with an error naming them (`contacts.persona_template_id` is `ON DELETE RESTRICT`; the service check exists so the failure is legible rather than "FOREIGN KEY constraint failed"). Deleting a Skill succeeds and strips its id from every persona's `skill_ids` in one transaction — `skill_ids` is a JSON array with no FK behind it, and a skill is injected text, so losing one degrades a persona's instructions rather than breaking the persona. Blocking there would have forced hand-unattaching it everywhere first.
- **`PRAGMA foreign_keys = ON` is mandatory and easy to miss (2026-08-16, Phase 4):** better-sqlite3 leaves foreign keys **off** by default, which would make every `references()` in `src/main/db/schema.ts` decorative — including the RESTRICT the persona-delete rule above depends on. Set in `src/main/db/create.ts`, with a test that bypasses the service check and asserts SQLite itself blocks the delete, so it can't silently regress. Related: `cost_usd` is a REAL column, not the INTEGER that Drizzle's `integer()` would have made it — a turn costs fractions of a cent.
- **Two migrations, not one, to drop `_bootstrap_check` (2026-08-16, Phase 4):** drizzle-kit prompts about rename-vs-drop when a table disappears, and that prompt needs a TTY, so adding eight tables while deleting one fails outright in a non-interactive shell. Split into `0002_add_blueprint_schema` (additive only) and `0003_drop_bootstrap_check` (deletion only), which are each unambiguous and read better as history anyway.
- **`app_state` table is permanent (Phase 3; honoured by Phase 4):** Phase 3 adds a `app_state` key/value table (`drizzle/0001_pretty_warlock.sql`) holding `onboarding_completed`, `github_account_login`, `github_scopes`. Unlike `_bootstrap_check`, Phase 4 **inherited** this table rather than dropping it, and added `seed_version` to it. Non-secret metadata only — the encryption boundary is `src/main/services/secrets.ts`, the sole permitted `safeStorage` caller (enforced by a `no-restricted-properties` rule in `eslint.config.mjs`), which writes keychain-encrypted files to `userData/secrets/*.bin` rather than to SQLite so that "no credential is in the database" holds by construction.
- **Env var prefix — clarifies Phase 1 config (resolved 2026-08-16, Phase 3):** electron-vite exposes only `MAIN_VITE_`-prefixed `.env` vars to the main process; an unprefixed name is invisible to `import.meta.env`. Rather than force a rename of the existing `GITHUB_CLIENT_ID`, `electron.vite.config.ts` widens `envPrefix` for main to `['MAIN_VITE_', 'GITHUB_']`, and `github-auth.ts` reads either spelling. See `.env.example`. A device-flow client ID has no accompanying client secret, so build-time inlining is not a leak.
- **Launch splash added to Phase 3 scope (2026-08-16, at the user's request):** so the first-run path is complete end to end — splash → onboarding → shell, with no unstyled seam. Implemented in-renderer (`components/launch/SplashScreen.tsx`) rather than as a second `BrowserWindow`, because `src/main/index.ts` already suppresses the pre-paint gap via `show: false` + `backgroundColor` + `ready-to-show`; the only gap a user actually perceives is the `auth.getStatus` round trip, which only the renderer can observe. Held for a 650ms minimum so a warm start doesn't flash it, and cross-faded so the seam reads as intentional. `App.tsx` is now the launch-flow router.
- **Tests are part of finishing a phase (established 2026-08-16, retroactively for Phases 1–3):** Phases 1–3 all shipped with no tests and no harness — manual verification proved each phase once but left nothing behind to catch a regression in a later one. From here, a phase is not `Done` until whatever in it warrants tests has them, and the testing scope is called out as part of the phase rather than bolted on afterwards.
  Harness: **Vitest** (`vitest.config.ts`, two projects — `main` in node with `electron` mocked, `renderer` in jsdom) and **Playwright** for Electron E2E (`playwright.config.ts`, `e2e/`). `npm test` runs the unit suite and is now a gate inside `npm run build`, so packaging can't ship a red suite; `npm run test:e2e` builds first, then drives the real app. Judgement on what to cover: pure logic, state machines, and process-boundary contracts yes; purely presentational components that only render mock data, no.

- **Hide-on-close, and the two things it quietly breaks (2026-08-16, Phase 8):** macOS already kept the process alive on window close, so the tray is not what _enables_ residency — it is what makes it visible and quittable. That is what removes any need for a refresh interval — the menu is rebuilt only when a schedule changes or a routine finishes. Disabled routines are omitted entirely rather than listed as unscheduled, since a next-fire time for something that will never fire is a lie the menu tells every time it opens.
- **Cron validation is an IPC procedure, not a shared module (2026-08-16, Phase 8):** `src/shared/` has exactly one runtime dependency, zod, across all four files, and that is worth keeping — putting node-cron there would ship a scheduler runtime into the renderer bundle for a `validate()` call and leave `import { schedule } from 'node-cron'` one word away in renderer code. A hand-rolled shared validator is worse still: two implementations that can disagree, where the disagreement looks like a passing test. So the renderer asks main, keyed by expression with `staleTime: Infinity` so each distinct string costs one round trip _ever_ rather than one per keystroke — and main validates again on write, so a schedule the scheduler could not arm cannot reach the table by any route.
- **Run history is omitted from both write shapes (2026-08-16, Phase 8):** `routineUpdateSchema` omits `lastRunAt`/`lastRunSummary` as well as the draft doing so. Taking a whole `routineSchema` on update would let an editor open across a fire save its stale copy back over what the fire recorded, and the run would vanish with nothing to show it happened. Related: `lastRunAt` is stamped on every _attempt_ including a lock refusal, or the list renders "Never run" for a routine that has been skipping nightly for a week.
- **The E2E observes main through SQLite, not through a test hook (2026-08-16, Phase 8):** §15E's acceptance check is the one nothing existing could watch — `invoke` needs a renderer and `app.close()` ends the whole process. Resolved with `electronApp.evaluate()` for lifecycle (it runs in main and needs no window) plus reading the profile's database directly from the test process with **`node:sqlite`**, deliberately not better-sqlite3: `postinstall` rebuilds that against Electron's ABI, so loading it under plain Node works by luck of prebuild selection. A `globalThis` hook into main was rejected — shipping a backdoor to production to make a test convenient, when the acceptance check is about durable state anyway. The turn is not expected to succeed: the throwaway profile has no credentials, so it fails fast and the non-null `last_run_at` written with no window on screen is the entire proof. Asserting on a real reply would bill every E2E run.

- **A worktree's git writes land outside the worktree (2026-08-16, Phase 12):** the phase doc said `SessionSpec.repoPath` becomes the worktree path "with **no change to `sandbox.ts`**". That was wrong, and it is the finding the whole phase turns on. A linked worktree's `.git` is a _file_ pointing at `<repo>/.git/worktrees/<name>`, so the index, every new object and every ref update land outside the working directory — a sandbox fenced to the cwd fails at `git add`, not at some exotic operation. Reproduced twice before writing any code: with a hand-written seatbelt profile, and under Codex's own sandbox via `codex sandbox`. The fix is a **narrow** grant — `.git/worktrees/<name>` + `objects` + `refs` + `logs`, verified sufficient for a commit — carried on `SessionSpec.writablePaths` and applied as Claude's `allowWrite` and Codex's `--add-dir`. It deliberately excludes `.git/hooks` and `.git/config`: a writable hooks directory is a sandbox _escape_, since a hook written during a turn runs unsandboxed on the user's next git command. The per-worktree directory is read from git rather than derived, because git dedupes it from the path's basename (`work`, `work1`).
- **§6 degrades to "the object store is free" (2026-08-16, Phase 12):** measured, not argued. Fully write-fenced, `git show <branch>:<file>`, `git diff main...<branch>`, `git log` and `git status` all succeed from inside a worktree _and_ from the main tree. So a reviewer can read a refactor that exists nowhere on their own disk, without a merge and without elevated permission — which is what saves Journey 2 step 3. `show`/`diff`/`log` were already on the read-only allowlist; `git branch` and `git worktree` were **not**, and were deliberately left off, since `worktree` cannot be allowed for listing alone (add/remove/prune share the token). The branch list is therefore injected by main instead.
- **The conflict dry run is `merge-tree`, not `merge --no-commit` (2026-08-16, Phase 12):** the doc proposed `git merge --no-commit --no-ff` as the pre-click check. That is a dry run that isn't — it leaves the target tree conflicted on failure, which is a poor thing to do to a directory somebody is working in. `git merge-tree --write-tree` merges entirely in the object store: exit 1 signals conflicts, `--name-only` lists the files, and HEAD and the working tree are untouched. There is a test asserting exactly that, so nobody "simplifies" it back.
- **Isolation says where; the sandbox says whether it locks (2026-08-16, Phase 12):** the doc's "`shared` — never locks" is wrong for a `workspace_write` Contact left in the main tree, and conflating the two axes would have quietly unlocked every writer that opted out of worktrees. So `lockModeFor` takes both, and only `exclusive` overrides the sandbox level — that being the mode whose whole purpose is to demand the main tree to itself, so it locks even for a reader.
- **The worktree path is planned at create, materialised at first turn (2026-08-16, Phase 12):** `startTurn` is synchronous and has to know the lock key before it can `acquire`, so it cannot wait on a `git worktree add`. Deriving the path deterministically at Contact create keeps `workingPathFor()` a pure function of the row from the very first turn, while the directory itself is only built when the Contact is actually used. `ensureWorktree` fails **loudly** rather than falling back to the main tree: the fallback would put a Contact the user isolated on purpose back in the directory they were protecting, with the run lock none the wiser because the key was decided from the row.
- **Branches are enumerated from git, not from the contacts table (2026-08-16, Phase 12):** a branch outlives the Contact that made it — `worktree remove` keeps it, and so does deleting the Contact. A test written from that claim caught the first implementation doing the opposite: it derived the repo list from contacts, so deleting the last contact hid its branch, which is precisely the case the panel exists for. It iterates Groups instead, which are per-repo and never removed with their members. Relatedly, `deleteContact` refuses by default when the worktree holds uncommitted work: committed work is safe either way, but uncommitted changes exist nowhere else.
- **Branch metadata is stamped by git, never asked of the model (2026-08-16, Phase 12):** `summary.ts` has carried a `branch` field since Phase 7 and it always came back null, because nothing ever told the model what the branch was — and a model-reported branch would be unverifiable even when it arrived. Main knows it from the row; the head and the changed-file list are two deterministic commands. The model's value survives only as the fallback for a session that switched branches itself. The `needs` request added alongside it needed a live strict-mode check on both backends before anything depended on it: **strict mode applies to nested objects too**, so it carries its own `required` and `additionalProperties: false`, without which it would have rejected _every_ summary rather than only the rare one that fills it in.
- **A worktree session will write into the git admin directory unless told where it works (2026-08-16, Phase 12):** found only by the live pass, and only on `claude-sonnet-5` — seven haiku runs and every Codex run passed. Asked to create a new file with a bare relative name, the model resolved it against `<repo>/.git/worktrees/<name>/` rather than its own working tree: the right basename, the wrong parent. That directory is writable because it holds the index a commit must lock, so the grant invited the mistake. Both layers refused it correctly and nothing escaped, but the turn failed to do its work. It never showed up in gate 1, which _edits an existing file_ and so hands the model an unambiguous path; it takes a **new** file to expose it, and personas create files constantly. Two fixes: the Claude adapter's denial message now names the refused target — without it the message was unactionable, and the diagnosis was impossible — and a session working outside its repo now gets a short block naming its working directory, its repo, its branch, and saying not to write inside `.git`. Clean on three sonnet runs afterwards, including the exact configuration that had failed. **No unit test could have caught this**: every one of them mocks the adapter, and a mocked adapter never resolves a path.
- **`npm run build` gates on the tests, which makes E2E mutation testing silently vacuous (2026-08-16, Phase 12):** disabling worktree materialisation and re-running the E2E showed all five specs still passing — which looks exactly like a suite with no teeth. It wasn't: `build` runs typecheck and the unit suite before `electron-vite build`, so a mutation worth making fails the gate, the bundle is never rewritten, and Playwright launches the _previous_ build. Rebuilding with `npx electron-vite build` directly, the same mutation fails four of the five. Noted in the spec's header, because the false negative is indistinguishable from a real one.
- **Cloning with a token in the URL left the token on disk (2026-08-16, Phase 9):** `cloneRepo` passed `withToken(cloneUrl, token)` to `git clone`, and git writes the URL it is handed **verbatim** into the new repo's `.git/config`. Every repo the app cloned therefore held a live GitHub token in a plaintext file inside a directory personas then work in — and `gitWritePathsFor` fences `.git` against _writes_, not reads, so any `read_only` persona could have read it. Reproduced against a real clone before fixing rather than reasoned about. The remote is scrubbed to the clean URL as part of the clone, and `pushBranch` passes its URL rather than configuring one, so nothing outlives the command. Recorded as not fixed: the token is still visible in the process argument list while git runs, which needs a credential helper on stdin.
- **A worktree session will also write into the _repository_ unless told not to (2026-08-16, Phase 9):** the entry above about the git admin directory was half the story. Journey 3's first live run asked for `src/<file>.ts` — a directory that existed in neither checkout — and `claude-sonnet-5` created it in the main repo, which is the other path the "Where you are working" block names. Refused correctly by both layers, so nothing escaped; the routine simply did no work. A missing parent directory sends a model looking for the canonical copy of a project, and naming a path in a prompt is not the same as saying what may be done with it. The block now says the repository is a different checkout and writing to it is refused. Two runs in the failing configuration pass afterwards.
- **A routine's own bookkeeping must not wait on GitHub (2026-08-16, Phase 9):** the first version of the post-run pull request recorded `lastRunAt`/`lastRunSummary` _after_ the attempt, putting a fire's record behind a network call with no deadline of its own — a hung Octokit request would leave a run that plainly happened looking like it never did. Caught by an existing scheduler test rather than in review. Recorded first, appended to afterwards.
- **A total that excludes something must say so — and the mocks had been manufacturing the excuse (2026-08-16, Phase 10):** `aggregateUsage` skipped every `costUsd === null` event and returned a plain number, so a mixed set rendered a confident `$12.34` short by whatever the unpriced turns cost. `formatCost` had been written carefully to print `—` for a _single_ unknown; the aggregate discarded that care the moment there was more than one event. Now `UsageSummary` carries priced/unpriced counts and `formatCostSummary` renders `$12.34+`.
  The reason it was tolerated for so long is the more interesting half. Six places asserted that "Codex reports tokens but no dollar figure (blueprint §3)", two of them user-visible, one naming the personas it applied to. That stopped being true in **Phase 5**, which built `pricing.ts`; `codex.ts:144` has computed a real Codex cost on every turn since. And `mocks/usageEvents.ts` _manufactured the evidence_ — every Codex fixture row was seeded `costUsd: null`, so the dashboard was narrating a story the fixtures existed to tell, and no amount of looking at the running app would have contradicted it. `costUsd === null` now means exactly one thing: the model has no row in `CODEX_PRICES`, which can happen on either backend. Worth generalising: a screen on fixtures is not evidence about the system, and a fixture written to match a belief will keep confirming it after the belief is false.
- **Spend from a turn nobody is watching needs its own announcement (2026-08-16, Phase 10):** usage was invalidated from `useAgentStream` on `done`, which only reaches a component subscribed to that specific `runId` and only while that thread is mounted — neither of which a scheduled routine satisfies. Watching the dashboard while a routine spent money showed a stale total indefinitely, which defeated the phase's first acceptance check.
  `runs-changed` is the obvious signal and the wrong one: `messaging.ts` fires `emitRunsChanged()` in its `finally` at :467 and only _then_ calls `summarizeTurn`, which records the summary turn's usage from `compaction.ts`. A runs-based refetch would arrive **before** the row it was meant to collect, so coordination spend would lag a turn behind forever. Resolved with a `usage-changed` push emitted from `recordUsage` itself — the single point all four sources pass through — after the insert, so it cannot race the row it announces. Subscribed inside `useUsageEvents` rather than in a component, so every consumer is covered by construction rather than by remembering.
- **`sdk` vs `computed` is recorded but not shown — user decision (2026-08-16, Phase 10):** `10-usage-cost-dashboard.md` scope item 3 asks the UI to "label estimates honestly using `cost_source`", on the reasoning that a figure Anthropic returned and one we computed from our own table are not the same kind of number. Overridden by the user: the distinction is not worth putting in front of someone reading a spend total. The column is still written per row, so the breakdown can be added whenever it is wanted. Recorded because the phase doc and the shipped UI otherwise disagree with no explanation.
- **Two gaps in cost honesty this phase could not close (2026-08-16, Phase 10):** the `+` marks turns with _no_ price, and neither of these is one. **(a)** `pricing.ts` has no context dimension, so a long `gpt-5.5`/`gpt-5.4` session is priced at the sub-272K tier — those rows have a price, just the wrong one, and render as fact rather than as a floor. All three hand-checked rows sit far under the threshold, so this is untested rather than disproven. **(b)** `contacts.delete` cascades `usage_events` away, so deleting a Contact silently shrinks every historical total that included it — the same class of dishonesty the phase set out to fix, needing `ON DELETE SET NULL` plus denormalised persona/repo columns and a migration.
- **Spend outlives the Contact that made it — migration `0008` (2026-08-17, post-Phase-10):** `usage_events.contact_id` was `NOT NULL` with `ON DELETE cascade`, so deleting a Contact took its spend with it and a total covering last month shrank when somebody tidied up a Contact this month. Spend is a record of money that was actually spent; no later bookkeeping makes that untrue. Now `set null`, matching what `group_messages` already does for a weaker version of the same reason — and because that alone would leave the row with no attribution at all, `persona_template_id` and `repo_path` are copied onto each row at write time, with the migration backfilling history by joining contacts as it copies. They are **plain text, not foreign keys**: the whole point is to outlive the rows they came from, and a `restrict` FK would make a persona undeletable for as long as any turn had ever run on it.
  Three things worth carrying forward. **(a)** SQLite cannot alter a FK, so this is a table rebuild — the first in this repo. drizzle's `migrate()` wraps every statement in one transaction and **SQLite ignores `PRAGMA foreign_keys` inside a transaction**, so the generated pragmas are no-ops and the rebuild runs with enforcement live. Survivable only because `usage_events` is a pure child; the same rebuild applied to a parent table would not be. **(b)** drizzle-kit's generated `INSERT` selected the two new columns from the _old_ table, which does not have them — the hand-edited `LEFT JOIN contacts` is what turns a broken copy into a backfill, and editing the data movement is safe because the snapshot describes the schema, not the copy. **(c)** The unit suite runs the real migration folder on every DB-backed test, but always against an empty table, so it proves the migration _applies_ and nothing about what it _copies_. The backfill needed its own upgrade test, and that test was mutation-checked: replacing the join with NULLs fails it.
- **A half-finished honesty fix is still dishonest (2026-08-17, post-Phase-10):** with attribution stamped on the event, the by-repo breakdown correctly showed a deleted Contact's spend under its real repo — while the dashboard's _scope_ filter still worked by contact id, so scoping to that same repo made the row vanish. Two totals on one screen disagreeing about the same money, with the more prominent one wrong. Found only because the E2E gained an orphaned row and its repo-scope assertion moved; nothing in the unit suite asked the question. `scopeFilter` now resolves persona and repo exactly the way the breakdowns do. Generalises: when a fact gains a new source of truth, every reader has to move together, and the readers are easy to enumerate and easy to miss.
- **Long context is priced per request, not per conversation (2026-08-17, post-Phase-10):** `pricing.ts` had no context dimension, so a `gpt-5.5` turn over 272K billed at the cheap tier — and unlike an unpriced model, those rows _have_ a price, so Phase 10's `+` marker did not cover them and they rendered as fact. Scaled from the observed turn, the gap was 47%. Now `longContext` rates on the rows that have them, selected on **one turn's own input tokens**: Codex reports cumulatively and the baseline is already subtracted by then, so the delta is that request's prompt, which is what the vendor prices. The consequence is stated rather than hidden — a long conversation whose individual turns each stay under the threshold is priced short throughout. Two transcription traps recorded on the way: the long rates are **not** a uniform multiplier (input and cached double, output rises by half, so `gpt-5.5` goes 30 → 45 rather than 30 → 60), and a first, loose read of the vendor page appeared to show `gpt-5.2`/`gpt-5.1` mispriced in the repo — a second targeted read disproved it. Verify a surprising figure before "fixing" a correct one.
- **The summariser follows the price list, and the rule is now enforced (2026-08-17, post-Phase-10):** `SUMMARY_MODELS.codex` moved `gpt-5.4-mini` → `gpt-5.6-luna`, which undercuts it 3.75x on both input and output (0.20/1.20 against 0.75/4.50). Compaction runs after _every_ turn, so this is the one model whose price is paid constantly. Cheaper in every case rather than on average — even luna's long-context tier (0.40/1.80) beats gpt-5.4-mini's flat rate, so no transcript size favours the old choice. A test now asserts no offered Codex model undercuts the summariser on **both** axes, so "cheapest" stops being a comment that quietly expires when a cheaper model is added; strict domination rather than a single ranking metric, because cheaper-on-one-axis-dearer-on-the-other is a genuine trade-off and a trade-off is a judgement call, not a test failure. **What this buys in cost it risks in quality, and nothing automated can see it:** a summariser picks a category, and a mis-categorised summary drops a turn's work out of every colleague's context — invisible where it happens, surfacing later as a colleague missing something it should have known. First thing to suspect if summaries start reading thin.
- **`cachedInput: null` means no discount, never free (2026-08-17, post-Phase-10):** the `-pro` models publish a $0.00 cached rate, which almost certainly means caching is unavailable rather than free. The two readings differ by the entire cost of the cached tokens, and over-reporting is the safe direction for a spend figure, so the type carries `number | null` and null bills at the input rate. No shipped row uses it — it exists so that adding a `-pro` model cannot quietly encode "free" — and the test installs a row to exercise the path, because an untested guard is a comment. Related: the `cachedInput < input` sanity loop had to learn to _skip_ nulls rather than compare them, since `expect(null).toBeLessThan(5)` passes by coercion and would have endorsed the one value it exists to catch.
- **Renderer logic that is not in `lib/` is untestable by construction (2026-08-16, Phase 10):** the Vitest renderer project matches `src/renderer/**/*.test.ts` — **not `.tsx`** — and `@testing-library/*` is not a dependency, so there is no component-render harness and coverage deliberately excludes components. That is a constraint on where code goes, not just on what gets tested: the dashboard's filtering, bucketing and four breakdowns all live in `lib/usage-report.ts` as pure functions, and the component picks filters and renders. A `UsageDashboard.test.tsx` would have been silently ignored by the runner rather than failing loudly.
- **`githubScope` is enforced in the service, not the button (2026-08-16, Phase 9):** `OpenPRButton` has returned `null` for `read_only` since Phase 2, and until Phase 9 that was the entire enforcement — the procedure behind it was callable by anything that could reach the bridge. Blueprint §13 is right that this is "a permission label on the persona, not hard-enforced beyond what the token itself allows"; what the app owes is one gate, placed where the action happens. Worth carrying into Phase 14, where an MCP tool could reach GitHub by a route that walks straight around it.
- **The app never authors a commit (2026-08-16, Phase 9):** a turn can end with a dirty working copy, and the tempting fix is to commit on the persona's behalf so an unattended run is not wasted. Refused on both the clicked and the routine path: the first commit this app ever authored should not be an unattended one, made of work nobody has read. The refusal names the files instead, following `mergeIntoWorkingPath`'s existing precedent for a dirty tree.
- **The app was never sealed on Codex — corrects Phases 5 through 13 (2026-08-17, Phase 14):** `claude.ts` has passed `settingSources: []` since Phase 5 with a comment reading "a persona's instructions are the persona's alone", and every document afterwards repeated that as a property of the _app_. ### Found in the Phase 6/7 live close-out (2026-08-16)

Five findings, all from running the thing rather than reading it. Three were defects that
every unit test agreed with, which is the point: the suite proves the tests agree with the
code, and the code and the tests were wrong together.

- **Claude's usage under `resume` is per-turn; Codex's is cumulative (settled 2026-08-16):** `06-core-messaging-handoff.md` §11 item 10 carried this as unverified, reasoned from SDK docs about _streaming-input_ sessions. Three turns on one resumed Claude session: `$0.2273`, `$0.2268`, `$0.0116`, with `modelUsage` reporting 2 in / 3 out every time. A cumulative figure cannot go down — **per-turn confirmed, `claude.ts`'s header assertion stands, and no delta arithmetic is needed.**
  Codex is the opposite, and nothing said so. The same three-turn shape, three one-word replies: output tokens `5 → 10 → 15`, input `12122 → 25610 → 39114`. That is a running sum, and `@openai/codex-sdk`'s own typings document every field as usage "during the turn" (`dist/index.d.ts:119-131`). Every Codex `UsageEvent` after the first over-reported by a margin that grew with the conversation — turn 3 billed `$0.066` against a true incremental cost of about `$0.011`. Fixed by subtracting a baseline: migration `0006` adds `usage_events.session_id`, and `baselineFor()` sums the deltas already recorded for that session. Since every stored row _is_ a delta, their sum is exactly the backend's next cumulative reading — no separate cursor to keep in step and nothing to repair if a turn crashes before recording. Rows predating the column carry NULL and are excluded, so an in-flight thread over-reports once more and is exact after; cheaper than a backfill that would have to guess which historical rows were which. The adapter does the subtraction and the caller resolves the baseline, the same division as `skills` and `groupContext`, because nothing under `adapters/` may query.
- **The first turn of every Claude session was attributed to the wrong model (2026-08-16):** `usageFromResult` named whichever model produced the most output tokens. The SDK makes an internal haiku call on every session start and it out-talks the main loop. Measured on a fresh session with the main loop on sonnet-5: haiku 521 in / 11 out / `$0.000576`, sonnet-5 2 in / 5 out / 27911 cache-write / `$0.167547`. The dashboard would have shown `$0.168` against haiku, on the strength of the model responsible for 0.3% of it. Now picks by `costUSD`, with output tokens as the fallback — cost is the honest tiebreak for a figure that is itself a cost. Fires on the _common_ case, not an edge one.
- **A `workspace_write` persona could escape its own OS sandbox (2026-08-16):** the entry above claimed OS enforcement; §11 item 11 asked for proof, and the proof failed. A persona bound to a scratch repo was asked to run `echo escaped > /tmp/outside-the-repo.txt`. - **A NUL byte in a source file makes it invisible to grep (2026-08-16, Phase 13):** `BranchDetail.tsx` joined a React key with a literal `\0` (`` `${repoPath}\0${branch}` ``). It works — no path or branch name can contain one, which is presumably the appeal — but a file containing a NUL is a _binary_ file to grep, and grep says nothing when it skips one. `file` reports it as `data`. So the file silently drops out of every grep-based sweep over the repository, and the failure mode is not an error, it is an answer that looks complete. It cost something immediately: the Phase 13 type-scale codemod found its files with `grep -rl`, so that file was never in the list and two `text-[11px]` survived a commit whose whole claim was that none had. Use a readable separator. `find src -name '*.tsx' -exec file {} + | grep -v text` finds this class of problem and returns nothing as of `05eb2c7`.
